# Arc Virtual Cell Challenge 2026 官方信息核验

> 状态：2026-08-30 公开信息快照  
> 范围：只核验赛题、数据、评分、提交与外部资源边界；不下载数据，不替项目选择科学路线。  
> 证据原则：优先采用 Arc Institute、Virtual Cell Challenge 官方站、官方 CLI 文档及 ArcInstitute 官方 GitHub。若规则与其他说明冲突，以正式规则为上位依据；规则未覆盖的技术细节保留版本冲突，不自行消解。

## 1. 结论摘要

1. 2026 赛题是**跨细胞背景的 zero-shot CRISPRi 响应预测**，不是在同一细胞系内对未见扰动做插值。Arc 共测量六个来自不同组织来源的细胞系；验证阶段使用匿名 context A/B/C，最终测试使用另外三个匿名 context D/E/F，真实细胞系名称不公开。[Arc 2026 公告](https://arcinstitute.org/news/virtual-cell-challenge-2026)；[官方数据说明](https://virtualcellchallenge.org/datasets)；[官方评测说明](https://virtualcellchallenge.org/evaluation)
2. 2026 **没有赛题专属训练集**。每个目标 context 只公开 NTC 单细胞 raw counts 和待预测基因列表；扰动后实验数据全部隐藏并作为 ground truth。[官方数据说明](https://virtualcellchallenge.org/datasets)
3. 每轮要求预测 `300 perturbations × 400 cells × 3 contexts = 360,000 cells`，基因轴固定为 18,533 genes；提交必须是单一 `.vcc` 文件中的 raw、非负、有限、整数意义 counts。[官方数据说明](https://virtualcellchallenge.org/datasets)；[官方 CLI 指南](https://vcc-cli-wiki.virtualcellchallenge.org/)
4. 2026 正式评分不是 2025 的 PDS/DES/MAE 三指标口径，而是 `cell-eval2` 的六项 `vcc2026` 指标，经 context 内 reference scaling 后在六指标与三个 context 间等权平均。[官方评测说明](https://virtualcellchallenge.org/evaluation)；[ArcInstitute/cell-eval2](https://github.com/ArcInstitute/cell-eval2)
5. 官方明确允许使用 2025 H1 hESC 数据，以及任何有合法使用权的公开或私有数据。因此，本项目 v2 中“若 2026 目标细胞系为 H1，则 2025 H1 不得进入训练域”的警告**没有当前官方依据，并与官方明确许可冲突**。由于目标 cell line 身份本来就不公开，也不应把“猜测目标身份”设为工程 gate。[官方数据说明](https://virtualcellchallenge.org/datasets)；[官方 FAQ](https://virtualcellchallenge.org/faq)
6. 最终预测必须由一个或多个机器学习模型产生；不得把实验结果或论文中的结果直接塞入提交，也不得以这些结果人工修改模型预测，但可以把有权使用的实验或文献数据用于训练或微调。[官方规则](https://virtualcellchallenge.org/rules)
7. 当前官网/CLI 与官方 `cell-eval2` 2026 metric specification 在“每扰动预测细胞数”和“是否包含 NTC 行”上存在实质冲突。工程上必须保留该冲突，并在每次正式提交前以**当时版本的 `vcc prep --dry-run` 和服务端验收**作为操作合同。[官方 CLI 指南](https://vcc-cli-wiki.virtualcellchallenge.org/)；[2026 metric specification](https://github.com/ArcInstitute/cell-eval2/blob/main/docs/vcc2026_metrics/vcc2026-metrics-brief.md)

## 3. 官方数据合同

### 3.1 每轮固定规模

| 项目 | 当前官方值 |
| --- | ---: |
| 匿名 cell contexts | 3；验证 A/B/C，终测 D/E/F |
| 每 context 提供的 NTC cells | 18,400 |
| 每 context 的 NTC guides | 46；每 guide 400 cells |
| NTC median depth | 约 20,000 UMIs/cell |
| 基因轴 | 18,533 genes |
| 待预测 perturbations | 300；同一轮三个 contexts 共用同一 panel |
| 每 perturbation、每 context 的预测 cells | 恰好 400 |
| 完整提交 | 360,000 cells |

以上规模由[官方数据说明](https://virtualcellchallenge.org/datasets)、[官方评测说明](https://virtualcellchallenge.org/evaluation)和[官方 CLI 指南](https://vcc-cli-wiki.virtualcellchallenge.org/)共同给出。验证和最终测试使用不同 cell lines、不同 perturbation panels，并分别使用各自的评分 anchors，两个阶段的分数不能直接横向比较。

### 3.2 控制数据 bundle

验证阶段的 `controls.zip` 约 630 MB，根目录包含：

| 文件 | 内容 |
| --- | --- |
| `context_A.h5ad`、`context_B.h5ad`、`context_C.h5ad` | 每个文件为 `18,400 × 18,533` 的 NTC raw-count AnnData |
| `gene_names.csv` | 18,533 个 gene symbols 及官方顺序 |
| `pert_counts.csv` | 300 个待预测 `target_gene` gene symbols |
| `manifest.json` | season、partition、panel id、contexts、各 context cell counts |

每个 control file 的 `.obs` 包含 `target_gene=non-targeting`、不可改写的 `context` 标签，以及标识 46 个 NTC guides 的 `ntc_id`。最终测试 bundle 在 10 月 22 日发布，结构相同但 context 改为 D/E/F。[官方数据说明](https://virtualcellchallenge.org/datasets)

### 3.3 数据进入本项目后的边界

本项目已完成数据获取、尚待用户手工复制，因此工程计划应从以下接收动作开始，而不再包含数据调研或下载：

1. 对复制完成的源文件做只读 inventory、checksum、可读性和 schema 核验；原文件进入不可变 raw 层。
2. 将 raw counts、原始 `.obs/.var`、gene order、context 标签和官方 manifest 保留为可追溯事实；清洗、归一化、HVG、PCA/UMAP 等仅写入派生层。
3. 分析矩阵和提交矩阵必须分离：分析可产生 normalized/log-transformed views，提交 `.X` 只能是 raw integer counts。
4. context 标签从读入到提交保持附着于数据对象；不能依据聚类或 UMAP 重新命名 A/B/C 或 D/E/F。

这些是由官方输入/输出合同导出的工程约束，不是对模型科学路线的裁决。[官方 CLI 指南](https://vcc-cli-wiki.virtualcellchallenge.org/)

## 4. 提交文件与验收合同

提交由一个 AnnData H5AD 经 `vcc prep` 封装成单一 `.vcc` 文件；三个 context 必须在同一文件中。[官方评测说明](https://virtualcellchallenge.org/evaluation)

当前官网与 CLI 要求如下：

| 合同项 | 要求 |
| --- | --- |
| `.obs['context']` | 精确保留 A/B/C 或 D/E/F；不得互换、遗漏或新增 |
| `.obs['target_gene']` | gene symbol，例如 `ADNP`；不能使用 guide/construct id，例如 `ADNP-1` |
| perturbation set | 每个 context 恰好包含 `pert_counts.csv` 中全部 targets；无额外项、无缺失项 |
| cells | 每 target、每 context 恰好 400；总计 360,000，且整文件不得超过 400,000 cells |
| `.var` | 恰好 18,533 genes，匹配 `gene_names.csv`；工具可按官方顺序整理 |
| `.X` | raw counts；有限、非负、整数意义；float dtype 中的整值可接受 |
| per-cell library | 所有 gene counts 总和不得超过 1,000,000 |
| controls | 提交不得包含任何 `non-targeting` rows；官方 NTC 仅作为模型输入和评分 reference |
| 稀疏度 | 全矩阵 stored entries 不得超过 4,750,000,000；显式存储的零也计数 |

一个 dense `360,000 × 18,533` 矩阵会存储 6,671,880,000 entries，直接超过上限；因此输出必须清除显式零并采用稀疏格式。官方建议若仍接近上限，可评估将约 1 CPM 以下值置零，但这是会改变模型输出的操作，必须先在内部验证其影响并登记，而不能无记录地作为文件压缩技巧。[官方 CLI 指南](https://vcc-cli-wiki.virtualcellchallenge.org/)

推荐的合同测试命令由官方给出：

```bash
vcc prep prediction.h5ad \
  -g gene_names.csv \
  --perts pert_counts.csv \
  -o prediction.vcc \
  --dry-run
```

正式封装时移除 `--dry-run`，提交使用 `vcc submit prediction.vcc -m "<model-id>" --wait`。CLI 会校验 gene set、contexts、perturbation labels、每扰动 cell counts、raw-count 和 no-control-cells 条件。[官方 CLI 指南](https://vcc-cli-wiki.virtualcellchallenge.org/)；[CLI command reference](https://vcc-cli-wiki.virtualcellchallenge.org/cli-reference)

## 5. 2026 六指标评分

官方使用开源 `cell-eval2` 的 `vcc2026` profile。[ArcInstitute/cell-eval2](https://github.com/ArcInstitute/cell-eval2)

| 榜单别名 | 正式 metric id | 主要测量内容 | raw 方向 |
| --- | --- | --- | --- |
| `pds` | `pds_cosine` | 预测 effect 是否与其自身真实 perturbation effect 比其他 perturbations 更接近 | 越高越好 |
| `mse` | `expr_mse_unbiased_capped_norm` | 扣除有限采样噪声后的表达误差相对真实 effect size 的比例 | 越低越好 |
| `nmae` | `de_wilcoxon_lfc_nmae` | 真实显著 genes 上 log2 fold-change 幅度的归一化绝对误差 | 越低越好 |
| `fid` | `de_wilcoxon_direction_fidelity_yield_raw` | 预测显著 genes 的响应方向是否正确，并惩罚调用过少 | 越高越好 |
| `reach` | `de_wilcoxon_direction_reach_raw` | 在预测置信排序中，方向纯度保持到多深 | 越高越好 |
| `jac` | `de_wilcoxon_sig_jaccard` | 预测与真实显著 gene sets 的 Jaccard 一致性 | 越高越好 |

精确定义见[官方 2026 metric specification](https://github.com/ArcInstitute/cell-eval2/blob/main/docs/vcc2026_metrics/vcc2026-metrics.md)及其[简版参数表](https://github.com/ArcInstitute/cell-eval2/blob/main/docs/vcc2026_metrics/vcc2026-metrics-brief.md)。关键实现参数为：

- DE 使用双侧 Wilcoxon rank-sum；按每个 perturbation 独立做 Benjamini-Hochberg 校正，阈值 `adjusted p < 0.05`。
- DE 只检测官方 reference control 中均值高于 5 CPM 的 genes；fold change 使用按 cell 归一到 `10^6` 后的算术均值。
- 所有六指标都排除 target gene；`pds_cosine` 更严格地从所有距离比较的固定特征空间中移除该轮全部 300 panel targets。
- `pds` 与 expression metric 对 group counts 做 pseudobulk，标准化至 50,000 后取 `log1p`；提交本身仍必须是 raw counts。
- `reach` 的方向纯度门槛为 0.9；`nmae` 只评估 reference 至少有 10 个合格显著 genes 的 perturbations。

### 5.1 Reference scaling 与 Overall

每个 metric 在每个 context 中都由两个实验内参照点缩放：

- `0`：该 context 的 mean-response baseline，即对所有 perturbations 预测相同平均响应；
- `1`：真实实验数据的 split-half replicate 水平，使用五次互斥拆分平均；
- `>1`：优于该实验 replicate anchor，允许出现；
- `<0`：差于 context-mean baseline，也属于正常数值而非缺失。

Overall 是六个 scaled metrics 在三个 contexts 上的无权重平均。它不是百分比，1 不是统一上限。验证和最终测试的 cell lines、panels、anchors 不同，所以两个阶段得分不可直接比较。[官方评测说明](https://virtualcellchallenge.org/evaluation)；[官方 CLI 指南](https://vcc-cli-wiki.virtualcellchallenge.org/)

### 5.2 对本地设计文档的更正

[技术路线与项目设计-v2.md](../../技术路线与项目设计-v2.md) 第 11 节仍以“PDS、DES、MAE + 若干相关性指标”描述正式评测，属于 2025/早期口径，不能作为 2026 提交优化的评分合同。工程实现应：

1. 直接锁定官方 `cell-eval2` 的 `vcc2026` preset，而不是自行重写“近似指标”；
2. 同时保存六项 raw metric、scaled metric、overall、partition、panel、anchor set、CLI/scorer version；
3. 在外部数据的 LOCO/双留出验证中报告官方六指标，同时继续保留科学上有解释力的辅助指标；两者不能互相替代。

## 7. 外部数据、模型与披露边界

### 7.1 明确允许

- 可使用任何有权用于本比赛的公开或私有数据，包括专有数据；Challenge 不要求获得这些训练数据本身。[官方 FAQ](https://virtualcellchallenge.org/faq)
- 官方明确允许使用 2025 H1 hESC Challenge 的训练、验证和已公开 held-out test 数据，并把它列为推荐资源；也推荐 Arc Virtual Cell Atlas、Replogle 2022、Nadig 2025、Jiang 2025 等公开资源。[官方数据说明](https://virtualcellchallenge.org/datasets)；[Arc Virtual Cell Atlas 2025 VCC 说明](https://github.com/ArcInstitute/arc-virtual-cell-atlas/tree/main/virtual-cell-challenge)
- 可使用 proprietary models。Arc 不因参赛获得参赛者模型的所有权。[官方 FAQ](https://virtualcellchallenge.org/faq)
- Arc State code 可在遵守其许可证的前提下参赛；预训练 checkpoints 对非商业参赛者适用相应非商业许可，商业参赛者需按官方流程获得许可。[官方 FAQ](https://virtualcellchallenge.org/faq)；[STATE model license](https://github.com/ArcInstitute/state/blob/main/MODEL_LICENSE.md)

### 7.2 明确禁止或需约束

- 不得使用无权用于本比赛的 property、know-how、code、information 或 data。[官方规则](https://virtualcellchallenge.org/rules)
- leaderboard 与 final predictions 必须由一个或多个机器学习模型生成。不得直接提交实验室结果或论文中已发布的结果，也不得用这些结果人工修订模型生成的 predictions；但这些材料可以在拥有使用权时用于训练或微调模型。[官方规则](https://virtualcellchallenge.org/rules)
- 因此，UMAP 与人工评估可以用于输入 QC、实现错误诊断、分布异常检查和预先定义的模型选择，但最终预测必须保持为可追溯的模型输出。人工查看不能转化为按外部真实响应或文献结论逐 target 手改提交。

规则的“Machine Learning Predictions Only”与 finalist 披露条目中要求说明“classical statistical, mechanistic, or otherwise non-learned components”同时存在。这表明官方预期可能有混合管线，但**纯未学习机制、人工规则或机制后处理在何种程度上仍算由 ML model 产生**并未被公开文本完全界定。若 GRN-ODE 管线包含未训练的规则融合或人工后处理，应在实施前向 `help@virtualcellchallenge.org` 获取书面澄清，不宜自行扩大许可。

### 7.3 代码与方法披露

一般参赛者不必提交模型代码或权重；Arc 可对可疑或 finalist submissions 要求补充核验信息。Finalist 若要获奖，必须提交将公开的高层方法说明，至少包括：

- 使用的训练数据；
- 数据处理与模型输入构造；
- 使用或改造的公开模型与其他模型；
- 非公开模型的相关架构说明；
- 统计、机制或其他非学习组件以及 output blending；
- 训练、适配和 inference-time 流程；
- 可选的 approximate compute resources。

因此，即便不开放代码，本项目也应从第一阶段开始保存 dataset registry、license、预处理版本、训练配置、随机种子、模型 lineage 与推理 provenance。[官方规则](https://virtualcellchallenge.org/rules)；[官方 FAQ](https://virtualcellchallenge.org/faq)

## 8. 官方来源间的未解决冲突

### U-001：预测 cell count 与 NTC 行

当前[官方数据页](https://virtualcellchallenge.org/datasets)、[官方评测页](https://virtualcellchallenge.org/evaluation)、[官方 FAQ](https://virtualcellchallenge.org/faq)及[官方 CLI 指南](https://vcc-cli-wiki.virtualcellchallenge.org/)一致要求：

- 每 perturbation、每 context 恰好 400 predicted cells；
- submission 不得包含 NTC rows。

但 2026-08-19 的[官方 `cell-eval2` metric specification 简版](https://github.com/ArcInstitute/cell-eval2/blob/main/docs/vcc2026_metrics/vcc2026-metrics-brief.md)仍写：

- “The number of predicted cells per perturbation is unconstrained”；
- perturbation labels 与 reference 完全匹配，“including the non-targeting control label”。

这是实质冲突，不应在文档中静默选择一个说法。当前可执行合同由 `vcc prep` 和服务端共同强制，因此本项目应以当时安装版本的 `vcc prep --dry-run` 结果为提交门槛；metric specification 只用于指标数学定义，不用于推导 submission schema。仍建议向主办方请求书面确认，并保存回复。

### U-002：`cell-eval2` 与 reference bundle 版本

公开 metric 文档注明参考数值基于 `cell-eval2 0.15.0`、competition `rule_version 3`；官方 GitHub 后续发布树已经更新到 0.16.0。公开 changelog 表明版本迁移涉及 bundle 与 provenance 管理，即使声称数值不变，也不能假定任意版本可与服务端 anchors 混用。[metric specification](https://github.com/ArcInstitute/cell-eval2/blob/main/docs/vcc2026_metrics/vcc2026-metrics-brief.md)；[cell-eval2 changelog](https://github.com/ArcInstitute/cell-eval2/blob/main/CHANGELOG.md)

工程上应锁定并记录：

- `vcc-cli` version；
- `cell-eval2` version 与 commit；
- `vcc2026` config snapshot/hash；
- competition `rule_version`；
- submission 返回的 partition、panel 和 anchor set。

不得仅写“用了最新版”，也不得把本地不同版本产生的分数直接与官方榜单比较。

### U-003：混合机制管线的“ML-only”边界

规则一方面要求 predictions solely generated by ML models，另一方面明确要求 finalist 披露 mechanistic/non-learned components。公开文本不足以判断完全未训练的 mechanistic output、人工融合权重或按 literature 手工调整参数是否允许。现阶段最强结论是：

- 学习得到的 GRN-ODE、统计估计器和固定的可复现推理链可以作为项目候选；
- 不能用实验或论文结果在 inference 后人工改写 target-specific predictions；
- 对未学习机制直接混入最终输出的边界，应向官方确认。

### U-004：最终 panel 与 authenticated bundle

最终 D/E/F 的具体 `pert_counts.csv`、control files、manifest 和实际校验规则要到 2026-10-22 才能取得。当前工程只能建立参数化合同和模拟 fixture，不能声称已经验证最终 panel。用户手工复制现有 validation/外部数据后，应先记录其真实文件名、checksum、shape 和 schema；这些不能由网页说明替代。

### U-005：规则仍可更新

正式规则声明 Arc 可调整规则或 scoring rubric，并会采取合理步骤通知参赛者；英文规则是控制版本。[官方规则](https://virtualcellchallenge.org/rules)

因此本文件是 2026-08-30 快照，不是永久合同。建议在每个提交 phase 开始时复核 rules、datasets、evaluation、FAQ、CLI guide 和 scorer release，并生成新的差异记录，旧快照保持不覆盖。

## 10. 进入工程计划前必须固化的合同

以下不是额外的数据获取阶段，而是用户完成手工复制后的工程起点：

1. **输入接收合同**：inventory、checksum、manifest、AnnData 可读性、raw-count 判定、`.obs/.var` schema、shape 和 gene-symbol 规范。
2. **不可变 raw / 派生数据分层**：所有清洗、筛选、格式转换、normalization、UMAP 和人工评估只产生带 provenance 的派生资产。
3. **官方指标 harness**：在外部数据的严格 OOD folds 上运行锁版 `cell-eval2 vcc2026`，另列科学辅助指标，不能混成一个未经定义的总分。
4. **submission contract test**：在模型研发前即构建 360,000-row 的轻量/基线 fixture，跑 `vcc prep --dry-run`；提交阶段不得首次接触格式合同。
5. **raw-count generator**：模型内部可在 normalized/program space 工作，但输出必须形成有限、非负、整数 counts，精确到 400 cells/target/context，并控制 library size 与稀疏度。
6. **context-label invariant**：A/B/C 或 D/E/F 从 bundle 读入后不可人工重映射；测试需覆盖 label swap、panel mismatch、gene-order mismatch 和 NTC leakage。
7. **人工评估边界**：UMAP/图形审查只作 QC、诊断和预注册模型选择证据；不得据隐藏响应、论文结果或手工 target knowledge 直接编辑最终 predictions。
8. **可披露 provenance**：自动生成 finalist 所需的训练数据、处理、模型、机制组件、训练/推理与 compute 摘要。
9. **提交冻结与重放**：D/E/F 路径应是 A/B/C 已冻结 pipeline 的参数化重放，只替换官方 bundle、contexts 与 panel；任何 final-phase 改动都需独立记录原因和验证。
10. **官方信息 refresh gate**：validation phase、final phase 和最终提交前分别复核规则/CLI/scorer，并保留页面访问日期、版本及差异。
